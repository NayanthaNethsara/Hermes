Yes, PostgreSQL is an ideal choice for this architecture.

### Benefits of PostgreSQL with `pgvector`

1. **Unified Storage Layer**:
   - Replaces fragmented ChromaDB files and multiple SQLite databases with a single relational database.
   - Houses ingestion tracking (`ingestion_tracker`), document metadata, and multimodal chunks in one schema.
2. **Dense Vector Search**:
   - Stores 1024-dimensional embeddings from Voyage Multimodal 3.5 using `vector(1024)`.
   - Supports HNSW indexing for rapid cosine similarity (`<=>`) queries.
3. **Built-in Sparse Keyword Search**:
   - Uses PostgreSQL full-text search (`tsvector` with GIN indexing and `ts_rank_cd`) or `pg_trgm` for exact proper noun matching, eliminating the need for a separate BM25 engine.
4. **Hybrid Search Execution**:
   - Dense vector retrieval and full-text keyword retrieval can be executed within the same database connection and fused via Reciprocal Rank Fusion (RRF).

Module Implementation Specifications
1. core/ — Infrastructure & Global Configuration
config.py:

Use pydantic-settings (BaseSettings) to read and validate environment variables: DATABASE_URL (PostgreSQL connection string), VOYAGE_API_KEY, GCP_PROJECT_ID, GCP_LOCATION, ASSETS_DIR, and score cutoff thresholds.

database.py:

Configure asyncpg engine and async session factory via SQLAlchemy 2.0.

Register the pgvector extension upon startup: CREATE EXTENSION IF NOT EXISTS vector;.

logging.py:

Initialize structured logging (structlog or standard library formatted for JSON) to trace document ingestion progress and agent node execution.

exceptions.py:

Define domain-specific exceptions (e.g., RetrievalThresholdError, DocumentParsingError) with FastAPI exception handlers.

2. data/ — Local File Storage
raw_archive/: Local mirror of the 415 corpus files (PDF, DOCX, MD, TXT, scanned images). Excluded from Git.

extracted_assets/: Output directory for cropped figures, diagrams, and tables extracted by the parser. Mounted by FastAPI as a static assets endpoint (/assets/...) so images can be served directly to the frontend.

3. ingestion/ — Layout Parsing & Indexing Pipeline
schemas.py:

Define Pydantic models for raw document metadata (doc_id, file_hash, source_category, epistemic_weight, file_path, page_number).

Define schemas for extracted elements (TextChunk, ExtractedFigure, ExtractedTable).

parser.py:

Integrate IBM Docling (DocumentConverter).

Perform layout analysis to identify text blocks, tables, and figures.

Extract bounding box coordinates, crop figure/table regions using Pillow, save .png files to data/extracted_assets/, and retain local path links.

chunker.py:

Split document text into semantically cohesive units (512–1024 tokens) while preserving parent section headings and associated figure file references.

embedder.py:

Batch calls to the Voyage AI multimodal embedding endpoint (voyage-multimodal-3.5).

Generate vectors for text chunks with interleaved image data.

Implement retries with exponential backoff (tenacity) to respect rate limits.

4. retrieval/ — Two-Stage Search Core
schemas.py:

Define SearchQuery, SearchResultChunk, and RankedResult Pydantic models.

vector_store.py:

Manage the PostgreSQL table schema:

id (UUID)

doc_id (VARCHAR)

file_hash (VARCHAR)

content (TEXT)

embedding (VECTOR(1024/1536)) with an HNSW index using cosine distance

tsv (TSVECTOR) for full-text search

metadata_payload (JSONB) holding file path, category, and image references

Execute Hybrid Search via Reciprocal Rank Fusion (RRF) directly in SQL, combining vector similarity (<=>) and keyword matching (ts_rank).

reranker.py:

Accept broad retrieval output (Top 30–50 candidates) and call Voyage AI rerank-2.5.

Enforce a strict relevance score cutoff (e.g., minimum score of 0.50). Drop candidate chunks falling below threshold to prevent model hallucinations.

router.py:

FastAPI endpoints (POST /retrieval/search) for direct retrieval queries without invoking agents.

5. agents/ — State Machine & Multi-Track Reasoning (LangGraph)
llm.py:

Initialize Google Cloud Vertex AI integration (ChatVertexAI using Gemini 1.5 Pro) with strict temperature settings (0.0–0.2).

state/base.py & state/models.py:

Define strongly typed state objects via typing.TypedDict or Pydantic:

root_query: Initial user prompt.

search_queries: Pending sub-queries to execute.

retrieved_context: List of verified chunks with relevance scores.

figures: List of local image paths for Track 1A.

facts: Key-value registry of extracted facts with credibility weights for Track 1C.

iteration_count and max_iterations to prevent infinite execution loops.

nodes/ (Action Components):

planner.py: Deconstructs complex inquiries into discrete search sub-queries.

retriever.py: Invokes retrieval/vector_store.py and reranker.py to populate state context.

evaluator.py: Compares newly retrieved facts against prior evidence; performs source credibility arbitration (e.g., official codex overriding folklore).

visualizer.py: Resolves bounding-box image paths to full asset URLs for Track 1A payload attachment.

synthesizer.py: Formulates the final response and forces structured output via Pydantic (answer_text, referenced_figures, citations).

graphs/ (Workflow Wiring):

multimodal_1a.py: Linear DAG (retriever -> visualizer -> synthesizer).

investigator_1c.py: Iterative state graph (planner -> retriever -> evaluator -> conditional edge looping back to retriever or advancing to synthesizer).

router.py:

FastAPI endpoints (POST /agents/run/{track_id}) to invoke the selected workflow graph with streaming or batched execution.

7. Root Files
main.py:

pyproject.toml:

End-to-End Execution Flow (Step-by-Step)
Step 1: Idempotent Offline Ingestion (workers/run_ingest.py)
Directory Walk: An independent CLI worker walks the /data/raw_archive/ folder containing the 415 mixed-format documents.

### How Images and Documents Are Actually Linked

There are 3 distinct visual integration patterns in the archive:

```
1. Markdown Lore (Wiki & Codex)
   ┌────────────────────────────────────────────────────────┐
   │ ![Weeping Lurker](images/atmo_creature_...png)          │
   │ # Weeping Lurker                                       │
   │ The Weeping Lurker is a nocturnal ambusher in Embermarch│
   └────────────────────────────────────────────────────────┘
   → Image appears inline immediately above the entity lore.

2. Codex & Manual PDFs (e.g. Codex Vaeloria II, Annals)
   ┌────────────────────────────────────────────────────────┐
   │ Page 12: Weapon Binding Rules                          │
   │ [Embedded Matplotlib Diagram: The Thrice-Bound Edge]   │
   │ "Attunement requires shards of will as shown above..."  │
   └────────────────────────────────────────────────────────┘
   → Diagrams and tables are embedded on specific pages alongside instructions.

3. Scanned Ephemera PDFs (*.scan.pdf)
   ┌────────────────────────────────────────────────────────┐
   │ Scanned Parchment Page (interrogation / letter / seal) │
   │ Handwritten / typewritten text embedded inside image   │
   └────────────────────────────────────────────────────────┘
   → The page itself is a visual artifact.
```

---

### The Problem With Naive Ingestion

If the parser and chunker do not maintain this flow:
1. **Broken Markdown Links**: The wiki text refers to relative paths like `images/atmo_xyz.png`, which fail to render in the frontend.
2. **Figure Bleed / False Context**: If a 50-page PDF has 1 diagram on page 12, a naive chunker attaches that diagram to all 50 pages. A search about page 2 would incorrectly cite the page 12 diagram.
3. **Missing Scanned Content**: Pure text extractors see empty text for scanned PDFs (`*.scan.pdf`) because the text is inside the scanned image.

---

### The Correct Context-Preserving Flow

Here is the exact pipeline to preserve context:

#### 1. In Markdown Parser ([`src/backend/ingestion/parser.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py))
- Detects `![alt](images/filename.png)`.
- Copies image to [`data/extracted_assets/{filename}`](file:///Users/nayanthanethsara/Documents/Github/Archivist/data/extracted_assets/).
- **Rewrites the inline markdown text directly to `/assets/{filename}`**.
- The chunk retains the inline image tag exactly where the author placed it.

#### 2. In PDF Parser ([`src/backend/ingestion/parser.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py))
- PyMuPDF extracts embedded diagrams and figures from each page.
- Saves them to [`data/extracted_assets/{file}_p{page}_{idx}.png`](file:///Users/nayanthanethsara/Documents/Github/Archivist/data/extracted_assets/).
- Injects an inline Markdown anchor `![Figure: Page {N}](/assets/{file}_p{page}_{idx}.png)` into that exact page's text.
- For scanned PDFs (`*.scan.pdf`), Gemini 2.5 Flash transcribes the handwritten text and historical stamps directly into that page's chunk.

#### 3. In Chunker ([`src/backend/ingestion/chunker.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/chunker.py))
- Scans each chunk's text for `/assets/{filename}`.
- **Strict 1-to-1 binding**: Only attaches figure references to the chunk if that figure actually appears in that specific section or page.

---

### 2. How Everything Is Stored

The storage layer is built entirely in **PostgreSQL 16 + pgvector** (running locally in Docker on port 5432) paired with a static asset directory.

```
PostgreSQL Database (`archivist`)
├── Table: `documents`           (Parent records & SHA-256 idempotency)

Local Filesystem
└── `data/extracted_assets/`     (Served as static HTTP assets at `/assets/...`)
```

Here is the exact schema and data model:

---

#### Table 1: `documents` (Parent Metadata & Idempotency)
Defined in [`vector_store.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/vector_store.py#L18-L32):

| Column | Type | Purpose |
| :--- | :--- | :--- |
| `file_hash` | `VARCHAR(64)` **PK** | SHA-256 hash of the raw file. Enables instant skipping of already-processed documents on subsequent runs. |
| `doc_id` | `VARCHAR(255)` | Clean document identifier (e.g. `weeping_lurker`, `codex_vaeloria_ii`). |
| `file_path` | `VARCHAR(1024)` | Original source path on disk. |
| `source_category` | `VARCHAR(50)` | `codex`, `wiki`, `novel`, `ephemera`, or `image`. |
| `epistemic_weight` | `FLOAT` | Trust/authority weight (Codex = 1.0, Wiki = 0.9, Novel = 0.7, Ephemera = 0.85). |
| `chunk_count` | `INTEGER` | Total number of chunks generated for this file. |
| `figure_count` | `INTEGER` | Number of extracted diagrams or images. |
| `created_at` | `TIMESTAMP` | Ingestion timestamp. |

---

#### Table 2: `document_chunks` (The Search & Evidence Store)
Defined in [`vector_store.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/vector_store.py#L35-L65):

| Column | Type | Purpose |
| :--- | :--- | :--- |
| `chunk_id` | `VARCHAR(255)` **PK** | Unique composite ID: `{file_hash[:10]}_{doc_id}_{sequence_index}`. |
| `doc_id` | `VARCHAR(255)` | References parent document ID. |
| `file_hash` | `VARCHAR(64)` | References parent `documents.file_hash`. |
| `content` | `TEXT` | The searchable text. For text docs, this contains paragraphs with inline `![Figure](/assets/...)`. For visual plates, this contains the verbatim text, gauge ratings, held objects, and visual scene analysis from Gemini 2.5 Flash. |
| `embedding` | `VECTOR(1024)` | 1024-dimensional dense vector generated by Voyage AI (`voyage-multimodal-3.5`). Indexed with an **HNSW cosine index** (`m=16, ef_construction=64`). |
| `tsv` | `TSVECTOR` | PostgreSQL full-text search vector (`to_tsvector('english', content)`). Indexed with a **GIN index** for fast keyword lookups. |

### How Retrieval Uses This Data

When a user query is received (e.g. *"What is the numerical rating of the Weeping Lurker?"*):
1. **Dense Vector Search**: Looks up the 1024-dim query vector using the HNSW index on `document_chunks.embedding`.
2. **Full-Text Search**: Matches exact keywords (`weeping`, `lurker`, `rating`) using the GIN index on `document_chunks.tsv`.
3. **Reciprocal Rank Fusion (RRF)**: A single SQL query fuses vector similarity and keyword rank into a final `rrf_score`.
4. **Context Assembly**: The retrieved chunk contains the text answer and its bound `figure_references = ["/assets/plate_08_creature_weeping_lurker.png"]`.
5. **Synthesizer**: Cites the exact rating and renders the diagram inline in Markdown for the frontend.

### Database Indexes

The table contains two high-performance indexes optimized for hybrid search:

1. **HNSW Cosine Vector Index**:
   ```sql
   CREATE INDEX ix_document_chunks_embedding_hnsw 
   ON document_chunks 
   USING hnsw (embedding vector_cosine_ops) 
   WITH (m = 16, ef_construction = 64);
   ```
   Provides sub-millisecond approximate nearest neighbor (ANN) vector similarity search.

2. **GIN Full-Text Search Index**:
   ```sql
   CREATE INDEX ix_document_chunks_tsv

   USING gin (tsv);
   ```
   Enables fast inverted-index keyword search across all document content.

3. **B-Tree Indexes**:
   Standard indexes on `doc_id`, `chunk_id`, and `file_hash` for fast relational joins and deletes.

### Where We Use Raw SQL (and Why)

For **Hybrid Search (Reciprocal Rank Fusion)** in [`hybrid_search_rrf()`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/vector_store.py#L121-L168), we execute optimized raw SQL via `text(...)`:

```sql
WITH vector_matches AS (
    SELECT chunk_id, doc_id, content, metadata_payload,
           ROW_NUMBER() OVER (ORDER BY embedding <=> CAST(:vector_param AS vector)) as vector_rank,
           (1 - (embedding <=> CAST(:vector_param AS vector))) as vector_score
    FROM document_chunks
    ORDER BY embedding <=> CAST(:vector_param AS vector)
    LIMIT :candidate_limit
),
keyword_matches AS (
    SELECT chunk_id,
           ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, plainto_tsquery('english', :query_param)) DESC) as keyword_rank
    FROM document_chunks
    WHERE tsv @@ plainto_tsquery('english', :query_param)
    LIMIT :candidate_limit
)
SELECT ...
FROM vector_matches v
FULL OUTER JOIN keyword_matches k ON v.chunk_id = k.chunk_id
ORDER BY (1.0 / (60 + v.vector_rank) + 1.0 / (60 + k.keyword_rank)) DESC;
```

**Why raw SQL here?**:
- Complex Common Table Expressions (CTEs) combining pgvector distance operators (`<=>`) with PostgreSQL `ts_rank()` are much cleaner and run significantly faster in raw SQL without ORM object overhead.
- The raw results are mapped immediately into type-safe Pydantic models ([`SearchResultChunk`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/schemas.py)).

     ```python
         reraise=True,
     )
     ```
     If Voyage returns an HTTP 429 (Rate Limit Exceeded), the client automatically pauses (2s, 4s, 8s... up to 30s) and retries without crashing the process.

### 2. Where Reranking Happens

Reranking happens during retrieval, right between the initial database search and the synthesizer.

It is implemented in [`src/backend/retrieval/reranker.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/reranker.py) and called inside the agent's retriever node ([`src/backend/agents/nodes/retriever.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/retriever.py#L36-L44)).

```mermaid
flowchart TD
    UserQuery["User Query"] --> EmbedQuery["Embed Query Vector (voyage-multimodal-3.5)"]
    EmbedQuery --> PostgresRRF["PostgreSQL Hybrid Search (RRF)<br/>Dense HNSW Vector + Full-Text Search (tsvector)"]
    PostgresRRF -->|Top 50 Raw Candidates| Reranker["Cross-Encoder Reranker (rerank-2.5)<br/>src/backend/retrieval/reranker.py"]
    Reranker -->|Relevance Scoring & Threshold Cutoff| Top5Chunks["Top 5 High-Precision Chunks + Bound Figures"]
    Top5Chunks --> Synthesizer["LLM Synthesizer (Gemini 2.5 Flash)<br/>Answers query and embeds diagram inline"]
```

#### The Reranking Process:

1. **Step 1: First-Stage Retrieval (PostgreSQL RRF)**
   - PostgreSQL runs Reciprocal Rank Fusion combining pgvector HNSW cosine similarity and `tsvector` keyword rank to fetch **50 broad candidate chunks**.
2. **Step 2: Second-Stage Reranking ([`reranker.py`](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/reranker.py))**
   - Passes the query and all 50 candidate texts to Voyage AI's **`rerank-2.5`** cross-encoder model.
   - Unlike vector search (which compares pre-computed embeddings), `rerank-2.5` cross-attends the query words directly against the chunk content words.
   - It computes a true relevance score ($0.0$ to $1.0$).
3. **Step 3: Threshold Filtering & Top-K Selection**
   - Drops any chunks falling below `rerank_score_threshold = 0.50` (eliminating noise and irrelevant lore).
   - Selects the top 5 cleanest chunks.
4. **Step 4: Feeding the Synthesizer**
   - The top 5 chunks and their strictly bound figure URLs (`/assets/...`) are sent to `synthesizer.py` to draft the verified response.

### Graph Architecture

The `ask` pipeline (invoked via `make ask`, `POST /api/ask`, and `POST /agents/run/1a`) executes a LangGraph compiled state graph: **Track 1A Multimodal Graph** ([multimodal_1a.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/graphs/multimodal_1a.py)). 

For multi-hop iterative investigations, the system also implements **Track 1C Investigator Graph** ([investigator_1c.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/graphs/investigator_1c.py)).

```mermaid
flowchart LR
    Start([START]) --> Retriever[retriever<br/>Hybrid RRF & Rerank]
    Retriever --> Visualizer[visualizer<br/>Resolve Asset URLs]
    Visualizer --> Synthesizer[synthesizer<br/>LLM Grounding & Authority]
    Synthesizer --> End([END])
```

---

### Agent Nodes

#### 1. `retriever` ([retriever.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/retriever.py))
- **Embedding Generation**: Converts query into a 1024-dimensional dense vector using [MultimodalEmbedder](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/embedder.py).
- **Hybrid Search (RRF)**: Executes SQL Reciprocal Rank Fusion combining:
  - **Dense Vector Search**: pgvector HNSW cosine distance (`<->`).
  - **Sparse Keyword Search**: PostgreSQL full-text search (`plainto_tsquery('english', ...)` against GIN indexed `tsv` column).
- **Reranking**: Scores candidate chunks using [CrossEncoderReranker](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/retrieval/reranker.py) to select the top 5 most relevant chunks.
- **Figure Extraction**: Gathers all `figure_references` associated with the retrieved chunks.

#### 2. `visualizer` ([visualizer.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/visualizer.py))
- Inspects figure paths collected during retrieval.
- Maps internal file paths to API-accessible visual asset URLs (e.g., `/assets/atmo_relic_artifact_gauntlet_of_sorrowfell.png`).
- Populates `state["referenced_figures"]`.

#### 3. `synthesizer` ([synthesizer.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/synthesizer.py))
- Formats evidence blocks with explicit epistemic hierarchy headers:
  `[Source: doc_id] [Category: source_category (Authority: epistemic_weight)]`
- Instructs the LLM to strictly prioritize sources by authority (`Codex/Image: 1.0` > `Wiki: 0.8` > `Novel: 0.6` > `Ephemera: 0.4`).
- Instructs the LLM to flag contradictions in a structured list.
- Formats final response with markdown text, citations, referenced figures, and contradictions.

---

### Track 1C Iterative Graph Nodes (For Multi-Hop Questions)

In [investigator_1c.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/graphs/investigator_1c.py), two additional nodes enable iterative loop reasoning:

```mermaid
flowchart TD
    Start([START]) --> Planner[planner]
    Planner --> Retriever[retriever]
    Retriever --> Evaluator[evaluator]
    Evaluator -->|Insufficient & iter < max| Planner
    Evaluator -->|Sufficient| Visualizer[visualizer]
    Visualizer --> Synthesizer[synthesizer]
    Synthesizer --> End([END])
```

- **`planner`** ([planner.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/planner.py)): Uses the LLM to decompose complex queries into sub-queries.
- **`evaluator`** ([evaluator.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/evaluator.py)): Uses the LLM to check if gathered evidence is sufficient to answer the prompt; loops back to `planner` if missing information remains.
