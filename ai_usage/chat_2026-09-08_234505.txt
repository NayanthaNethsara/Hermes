### 1. Fine-Grained Image Byte Extraction and Canonical Hashing

- **Requirement**: The Ashen Era archive contains 70+ visual plates (heraldic banners, weapon diagrams, battle maps) embedded inside PDFs and DOCX files. - **Why Docling fell short**: Docling abstracts document conversion to a high-level markdown/JSON output. It does not expose raw image xref streams.
- **Why PyMuPDF & python-docx were used**:
  - In [parser.py:L365-L384](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py#L365-L384), PyMuPDF extracts raw `image_bytes` via `page.get_images(full=True)` and computes a SHA-256 hash (`hashlib.sha256(image_bytes).hexdigest()[:12]`).
  - This hash is matched against `self.plate_hashes` to link the image to its canonical entry, save it directly to `data/extracted_assets/`, and inject a rich `> **[Visual Evidence]**` markdown block directly adjacent to the image.
  - For `.docx` files, [parser.py:L289-L306](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py#L289-L306) inspects the XML relationship parts (`.//a:blip/@r:embed`) to extract raw image blobs with the exact same hashing logic.

---

### 2. Handling Scanned PDFs (`*.scan.pdf`)

- **Requirement**: Several archive documents (interrogation records, treaties, petitions) are scanned historical documents without an embedded text layer.
- **Why Docling fell short**: Docling relies on local OCR engines (such as EasyOCR or Tesseract), which are slow on CPU, require heavy dependencies, and struggle with historical fantasy typography and seal diagrams.
- **Why PyMuPDF was used**: In [parser.py:L396-L422](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py#L396-L422), PyMuPDF renders the page to a PNG via `page.get_pixmap(dpi=150)` and routes it through Gemini 2.5 Flash vision analysis. This produces accurate transcriptions and visual interpretations of scans with zero local OCR dependencies.

---

### 3. Execution Speed and Dependency Overhead

- **Docling**: Installs and loads large local PyTorch layout analysis models, Table Transformer models, and OCR weights. Running this over 63 PDFs and 50 DOCX files would take 15–30+ minutes, consuming several gigabytes of RAM.
- **PyMuPDF**: Built in C (MuPDF). It parses all 63 PDFs, extracts text and embedded plates, and writes assets to disk in **under 3 seconds** with negligible memory usage.

---

### 4. Deterministic Markdown Table Conversion

- For DOCX files, [parser.py:L320-L335](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/ingestion/parser.py#L320-L335) iterates through `document.tables` using `python-docx` and produces clean GitHub-flavored Markdown tables. This guarantees deterministic table structures without relying on model-based layout predictions.

### Current Architecture

Requests are currently handled as standard unary HTTP `POST` requests:
1. **Frontend**: [api.ts](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/frontend/lib/api.ts#L15-L42) sends a single `fetch` to `/api/ask`.
2. **Backend**: [router.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/router.py#L32-L88) executes the full LangGraph pipeline (embedding query, hybrid search, reranking, and LLM answer generation) and returns a complete `AgentRunResponse` JSON payload.
3. **Synthesis**: [synthesizer.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/synthesizer.py#L57-L96) prompts the model to output a single JSON structure containing `answer`, `referenced_figures`, `citations`, and `contradictions`.

---

### Is SSE (Server-Sent Events) Better?

**Yes, for user experience and perceived latency.**

#### Advantages of SSE
- **Reduced Perceived Latency (Time-To-First-Token)**: Instead of staring at a loader for 3 to 8 seconds while embedding, retrieval, reranking, and text generation finish, the user sees immediate feedback.
- **Workflow Visibility**: Multi-step workflows (like the iterative loop in [investigator_1c.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/graphs/investigator_1c.py#L17-L42)) can stream progress events such as `retrieval_started`, `query_refined`, and `evidence_found`.
- **Client Cancellation**: If the user cancels or closes the browser tab, the HTTP connection closes, allowing the backend to terminate LLM generation early and save API costs.

---

### Architecture Trade-Offs and Considerations

| Consideration | Unary HTTP POST (Current) | Server-Sent Events (SSE) |
|---|---|---|
| **Perceived Latency** | High (waits for full pipeline completion) | Low (tokens and step events stream immediately) |
| **Data Structure** | Simple: single JSON response with sources, figures, and answer | Requires typed event protocol (`event: status`, `event: token`, `event: done`) |
| **Agent Reasoning Steps** | Returned statically after pipeline completion | Can be emitted in real time as each graph node runs |
| **Caching / Retries** | Standard HTTP caching and idempotency mechanisms | Requires custom stream reconnection logic if interrupted |

---

### Implementation Requirements for SSE

Adopting SSE in this codebase requires addressing how structured metadata is handled:

1. **Separating Plain Text from Metadata**:
   - Currently, [synthesizer.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/synthesizer.py#L57-L58) forces the LLM to return valid JSON. Streaming tokens of a raw JSON string requires partial JSON parsing on the frontend.
   - With SSE, the preferred pattern is emitting metadata via typed event payloads, followed by streaming raw text tokens for the answer:
     - `event: metadata` -> sends `sources`, `reasoning_steps`, `referenced_figures`
     - `event: token` -> sends individual answer text deltas (`chunk.content`)
     - `event: done` -> signals completion with final contradictions or stats
2. **LangGraph Event Streaming**:
   - LangGraph provides `.astream_events()` natively, allowing nodes ([retriever](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/retriever.py), [evaluator](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/evaluator.py), [synthesizer](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/synthesizer.py)) to emit chunk events directly to a FastAPI `EventSourceResponse` (via `sse-starlette` or standard `StreamingResponse`).
3. **Frontend Reader**:
   - [api.ts](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/frontend/lib/api.ts) would use the browser `ReadableStreamDefaultReader` or `@microsoft/fetch-event-source` to append incoming tokens to the message buffer in [hermes-app.tsx](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/frontend/components/hermes-app.tsx).

In the current architecture, **an open-ended ReAct (Reasoning + Acting) loop does not happen on every prompt**.

Instead, Hermes runs a **deterministic 4-stage pipeline** with **metadata-based early-exit optimizations**, rather than an unbounded tool-calling loop.

### How Each Prompt is Currently Processed

The workflow in [workflow.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/graphs/workflow.py) follows a fixed graph:

$$\text{START} \longrightarrow \text{rewriter} \longrightarrow \text{retriever} \longrightarrow \text{arbitrator} \longrightarrow \text{synthesizer} \longrightarrow \text{END}$$

1. **Contextual Rewriter** ([rewriter.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/rewriter.py)):
   - Inspects conversation history in the current session.
   - If there is no previous history (first question in a session), it passes the prompt directly without complex context rewriting.
2. **Archive Retriever** ([retriever.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/retriever.py)):
   - Executes a single hybrid query (PostgreSQL dense vector cosine similarity + full-text keyword ranking via Reciprocal Rank Fusion) and collects associated visual plates.
3. **Early-Exit Arbitrator** ([arbitrator.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/arbitrator.py)):
   - **Early Decision**: Evaluates the retrieved chunk metadata before invoking any model.
   - If all retrieved chunks come from the same authority tier (for instance, only Codex entries and official plates), it **bypasses the LLM entirely** and returns in under 5 milliseconds.
   - It only triggers an LLM contradiction analysis when sources with differing credibility tiers (e.g. Official Codex vs. Ephemera rumors) disagree.
4. **Synthesizer** ([synthesizer.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/synthesizer.py)):
   - Generates the final answer with figure references and citations streamed directly to the frontend.

---

### Pipeline Architecture vs. Dynamic ReAct Loop

| Characteristic | Current Pipeline Architecture | Dynamic ReAct Agent Loop |
| :--- | :--- | :--- |
| **Execution Path** | Fixed DAG: Rewriter $\rightarrow$ Retriever $\rightarrow$ Arbitrator $\rightarrow$ Synthesizer | Iterative cycle: Thought $\rightarrow$ Action (Tool) $\rightarrow$ Observation until LLM stops |
| **Latency** | Low (1 LLM call for single turn; max 2-3 if rewriting or arbitrating) | High (3 to 6 sequential LLM calls, each adding 1-2s delay) |
| **Determinism** | High: Always retrieves citations and multimodal plates consistently | Variable: May loop or fail to call retrieval for nuanced queries |
| **Token Cost** | Predictable and minimal | High due to cumulative tool-calling message history |

---

### Potential Addition: Early Intent Routing

Currently, every prompt (even greetings like *"hello"* or meta-questions like *"who are you?"*) will search the archive database. 

If desired, an **early intent router** can be added at the start of the graph:
- **Direct Conversational Route**: Bypasses retrieval and arbitration for greetings, identity queries, or clarification requests, sending them directly to the synthesizer.

### Node Implementation Strategy

#### 1. Deterministic Guardrail (0 LLM Calls)
Instead of asking an LLM *"Is this question valid?"*, use lightweight deterministic checks:
- **Length & Injection Checks**: Sanitize input, empty checks, character bounds.
- **Intent Bypass**: If the query is a simple greeting (*"hello"*, *"who are you"*, *"thanks"*), route immediately to a direct conversational response without touching PostgreSQL, dense embedding models, or rerankers.
- **Cost**: **0 LLM calls**.

#### 2. Consolidated Context & Query Planner (0 calls for Turn 1, 1 call for Turn 2+)
Instead of having a separate Planner node **and** a separate Rewriter node:
- **Turn 1**: The user's query is already standalone. **Bypass the planner entirely (0 LLM calls)**.
- **Turn 2+**: A single, fast Gemini Flash call performs both pronoun resolution and sub-query planning:
  ```json
  {
    "rewritten_query": "What was the garrison strength of Emberdeep in 65 AS?",
    "sub_queries": ["Emberdeep garrison strength", "Emberdeep 65 AS founding"]
  }
  ```
- **Cost**: **1 LLM call** (only on follow-up turns).

#### 3. Archive Retriever (0 LLM Calls)
- Executes hybrid PostgreSQL vector cosine similarity + `TSVECTOR` keyword search via Reciprocal Rank Fusion (RRF).
- Reranks candidates using the Voyage `rerank-2.5` cross-encoder.
- **Cost**: **0 LLM calls**.

#### 4. Metadata-Driven Arbitrator (0 LLM Calls in ~90% of Queries)
- Evaluates the `epistemic_weight` metadata of retrieved chunks in Python.
- If all retrieved evidence comes from the same authority level (e.g. only Codex entries and official plates), **skip the arbitrator LLM entirely**.
- Only triggers contradiction analysis when sources with differing authority (e.g. Official Codex vs. Ephemera Ballads) disagree on facts.
- **Cost**: **0 LLM calls** (typically) or **1 LLM call** (rare conflict).

#### 5. Streaming Synthesizer (1 LLM Call)
- Streams the final response, citations, and figure plates directly to the user.
- **Cost**: **1 LLM call**.

#### 6. Asynchronous Title & Rolling Summary (0 User-Facing Latency)
- **Do not block the user's turn.**
- Once the `done` event is yielded, launch a non-blocking `asyncio.create_task()`:
  - **Title Generation**: After turn 1, generate a 3-word title (e.g., *"Emberdeep Garrison Audit"*).

async def screen_with_model_armor(prompt: str) -> tuple[bool, str]:
    template = os.getenv("MODEL_ARMOR_TEMPLATE")
    if not template:
        return True, ""

    try:
        from google.cloud import modelarmor_v1
        from google.api_core.client_options import ClientOptions

        location = os.getenv("GCP_LOCATION", "us-central1")
        client_options = ClientOptions(
            api_endpoint=f"modelarmor.{location}.rep.googleapis.com"
        )
        client = modelarmor_v1.ModelArmorAsyncClient(client_options=client_options)

        request = modelarmor_v1.SanitizeUserPromptRequest(
            name=template,
            user_prompt_data=modelarmor_v1.DataItem(text=prompt),
        )
        response = await client.sanitize_user_prompt(request=request)

        # Check if the prompt was flagged for prompt injection or policy violations
        if response.sanitization_result.filter_match_state == modelarmor_v1.FilterMatchState.MATCH_FOUND:
            return False, "Input flagged by security policy (prompt injection or prohibited content)."
    except Exception as error:
        logger.warning("model_armor_screening_failed", error=str(error))

    return True, ""

### 3. How "Tools" Are Handled: Deterministic Pipeline vs. ReAct Loop

In standard agent implementations, an LLM operates in an unbounded **ReAct (Reason + Act)** loop:
1. LLM decides which tool to call.
2. Tool executes and returns text.
3. LLM inspects output and decides whether to call another tool.
4. Loop repeats until the LLM decides to stop.

#### Why We Do Not Use an Unbounded ReAct Loop

- **Runaway LLM Calls**: An open ReAct loop often makes 5 to 10+ sequential LLM calls per turn, increasing cost and token consumption.
- **Unpredictable Latency**: Each ReAct iteration adds 1–3 seconds of roundtrip latency before the user sees the first streamed token.
- **Hallucinated Arguments**: Tool selection by LLMs can fail on edge cases, selecting the wrong search tool or passing malformed arguments.

#### The Archivist Approach: Dedicated Graph Nodes as Tools

Instead of giving an LLM a dictionary of tools to invoke iteratively, **tools are codified as deterministic nodes within the graph**:
- **Search Tool**: Encapsulated directly within [retriever.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/retriever.py). The Planner generates the search terms, and the Retriever executes vector search, full-text search, figure linking, and reranking without requiring an intermediate LLM call.
- **Evaluation Tool**: Encapsulated directly within [arbitrator.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/arbitrator.py), comparing epistemic confidence levels using deterministic logic before invoking the LLM only for actual conflicts.

This design ensures:
1. **Sub-second first-token latency** on streaming responses.
2. **Deterministic execution order**: Input safety $\rightarrow$ query planning $\rightarrow$ hybrid retrieval $\rightarrow$ source arbitration $\rightarrow$ streamed synthesis.
3. **Hard call cap**: Exactly 1 call on greetings, 1 call on Turn 1, and 2 calls on follow-up turns.

### Harnessing LLM Power for a Proper Agentic Approach

The current pipeline operates primarily as a fixed DAG with a basic fallback loop. To make it a genuine ReAct-style research agent:

#### 1. Activate Query Decomposition in the Planner
- Currently, [planner.py#L32-L42](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/planner.py#L32-L42) skips the LLM on the first turn:
  ```python
  if len(messages) <= 1:
      return {"search_query": root_query, "planned_queries": [root_query]}
  ```
- For complex, multi-hop questions (e.g., *"Which war was won by the organization that included Isolde Mournvale as one of its members?"*), passing the raw prompt into vector search dilutes retrieval quality.
- The planner must call the LLM to decompose questions into distinct investigative steps and extract targeted entity queries (e.g., `["Isolde Mournvale organization", "Isolde Mournvale faction"]`).

#### 2. Introduce Scratchpad / Chain-of-Thought Reasoning Before Decisions
- In both [critic.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/critic.py#L27) and [arbitrator.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/nodes/arbitrator.py#L42), the JSON schema forces the model to emit `"verdict"` or an array of contradictions immediately as the first token.
- Autoregressive LLMs cannot reason before generating output. Forcing an immediate verdict leads to premature `"answered"` decisions on partial keyword matches.
- **Solution**: Update the JSON schema to generate an `analysis` field first:
  ```json
  {
    "analysis": "1. Question asks for war won by X's organization. 2. Evidence identifies X belongs to The Silent Choir. 3. Evidence does not mention what war The Silent Choir won.",
    "verdict": "search_again",
    "missing_information": "Which war The Silent Choir won",
    "next_queries": ["The Silent Choir war victory", "The Silent Choir conflict won"]
  }
  ```

#### 3. Real-Time Streaming of Agent Reasoning Steps
- In [service.py](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/agents/service.py#L218-L248), the critic's reasoning step (why it decided to search again or how it analyzed the gap) is held until downstream nodes complete.
- Emitting the updated reasoning steps over SSE as each node finishes exposes the agent's thought process to the user in real time.
