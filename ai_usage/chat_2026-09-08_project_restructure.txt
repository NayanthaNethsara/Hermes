Your observation is correct. For a polyglot full-stack project (Python FastAPI + Next.js), putting `pyproject.toml` at the root versus inside the backend is an architectural trade-off.

---

### Why It Was Placed at the Root

1. **Existing Import Paths**:
   All 9 backend files currently use absolute imports rooted at `src`:
   ```python
   from src.backend import llm
   from src.backend.agents import critic, planner, synthesizer
   from src.backend.retrieval import graph_search, vector_search
   ```
   With [pyproject.toml](file:///Users/nayanthanethsara/Documents/Github/Archivist/pyproject.toml) at the root, the packaging tool considers `src` the root module, so existing code runs without modifying imports.

2. **Root Command Execution**:
   Root tools (`uv run ...`, `make backend`, linters, editor language servers) automatically discover `pyproject.toml` from the workspace root without requiring `--directory src/backend` flags or directory traversal.

---

### Why Scoping `pyproject.toml` to the Backend Is Often Better Practice

In a polyglot codebase containing both Python and Node.js:

1. **Isolation of Concerns**:
   - `src/frontend/` contains `package.json`, `node_modules`, `.next`, and `tsconfig.json`.
   - A root `pyproject.toml` forces Python build tools (Hatchling, Ruff, Mypy) to explicitly ignore frontend artifacts (`exclude = ["src/frontend"]`).
   - Scoping `pyproject.toml` to the backend keeps Python concerns strictly within Python directories.

2. **Package Portability**:
   - Inside `src/backend`, imports can become `from backend.agents import critic` or relative imports, rather than coupling the package namespace to an arbitrary `src` parent folder.
   - The backend can be containerized, tested, and published as a standalone service independent of the frontend.

---

### Architectural Options

| Aspect | Root `pyproject.toml` (Current) | Scoped `src/backend/pyproject.toml` | Top-Level `backend/` & `frontend/` |
|---|---|---|---|
| **Separation** | Mixed root (Python + Node) | Isolated backend configuration | Cleanest monorepo separation |
| **Import paths** | `from src.backend...` | `from backend...` | `from backend...` |
| **Build context** | Root scans whole repo | Backend only needs `src/backend` | Backend only needs `backend/` |
| **CLI usage** | `uv run ...` directly at root | `uv run --directory src/backend ...` | `uv run --directory backend ...` |

---

### Backend: [src/backend/Dockerfile](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/backend/Dockerfile)

#### Current Inefficiencies
1. **Broken Dependency Cache Layering**:
   `uv pip install -e .` is executed against an empty directory containing only `pyproject.toml` and `README.md`. It cannot install the editable package properly without the source files, and subsequent code edits bust the cache for `COPY . ./src/backend`.
2. **Runs as `root`**:
   The container executes as the default root user, violating container security best practices.
3. **Missing Python Environment Flags**:
   Missing `PYTHONUNBUFFERED=1` (can cause delayed/lost logs in `docker compose logs`) and `PYTHONDONTWRITEBYTECODE=1` (prevents `.pyc` clutter in container layers).

#### Recommended Optimizations
- Add standard runtime environment flags:
  ```dockerfile
  ENV PYTHONDONTWRITEBYTECODE=1 \
      PYTHONUNBUFFERED=1 \
      PYTHONPATH=/app
  ```
- Two-step install: copy only `pyproject.toml`, install dependencies into the system environment via `uv`, then copy source code. Code changes will take ~1 second to rebuild instead of reinstalling packages.
- Create and switch to a non-root system user (`archivist`).

---

### Frontend: [src/frontend/Dockerfile](file:///Users/nayanthanethsara/Documents/Github/Archivist/src/frontend/Dockerfile)

#### Current Inefficiencies
1. **Massive Image Size (~800MB - 1GB)**:
   The `runner` stage copies the entire `node_modules/` folder and runs `npm start`. In Next.js, this retains development tools and unneeded runtime packages.
2. **Missing Next.js Standalone Mode (~120MB)**:
   Next.js has built-in automatic output tracing (`output: "standalone"`). It bundles only the necessary files into `.next/standalone`, eliminating the need for `node_modules` in production.
3. **Runs as `root`**:
   Alpine provides a built-in unprivileged `node` user (`USER node`) that should be utilized.
4. **Missing Telemetry Disabling**:
   Next.js sends telemetry during build and startup unless `NEXT_TELEMETRY_DISABLED=1` is set.

---

### Optimization Impact Comparison

| Metric | Current Baseline | Optimized |
|---|---|---|
| **Frontend Image Size** | ~850 MB | **~130 MB** (85% reduction) |
| **Frontend Start Command** | `npm start` (overhead) | `node server.js` (instant boot) |
| **Backend Layer Caching** | Re-installs on code change | Reuses cached dependencies |
| **Backend Log Streaming** | Buffered (potential lag) | Immediate (`PYTHONUNBUFFERED=1`) |
| **Security Execution** | `root` (both) | **Unprivileged non-root users** |
